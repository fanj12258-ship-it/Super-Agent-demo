## 0. 改版背书：为什么必须双模（整次系统改版的核心）

> 这一节是产品立场，不是 UI 细节。后面所有 journey 都挂在这上面。

### 原来只有一种「正式用法」（四步法）——保留，但不再是唯一

经典链路大致是：

1. 整理需求  
2. 挖取业务知识  
3. 产出相关设计文档（产品设计 / 本体设计 / Agent 设计…）  
4. 建本体  
5. 再生智能体  

**问题（我们自己也踩过）：**

- 链路**特别长**，用户一开始做就容易 **lost**：我最终到底要得到什么？
- 价值出现得太晚——前面全是文档和准备，**很久才摸到一个能跑的 Agent**。
- 和很多人（包括你我）用 **Codex** 的真实习惯相反：希望简单扔一点输入 → 多轮对话先出个大概 → **先 POC 跑起来试用** → 哪里不行再回去改。

### 新增模式（本轮改版核心）：快路径 —— 先跑起来，再反向改结构

白话流程：

1. **简单输入** + **多轮 Agent 交互**  
2. 先帮你攒出**大概文档 / 雏形**  
3. **POC 跑出一个 Agent**，立刻能试用  
4. 试用中发现不足 → **反向**去改：本体、Skill、文档，以及文档里前期产品设计的前置依赖  
5. 全程要能看到两件事：  
   - **资产结构可视化**（有什么 / 缺什么；并不是每个 Agent 都必须有本体或 Skill——结构上要诚实展示「可选 / 未建 / 已有」）  
   - **Agent 本身长什么样**（可看、可试）  
6. 改完后要有 **一键同步**：试验里改的东西能同步回正式资产 / 正式环境，而不是两套对不上的世界  

快路径里可以有一些 **基础门档**（最低门槛），避免「瞎快」；但门档是服务「更快摸到可试用 Agent」，不是把人重新拖回长征。

### 两种模式的关系（必须写进 demo）

| | **新模式 · 快路径（POC ↔ 反改）** | **原模式 · 四步法（逐步正式）** |
|---|---|---|
| 心态 | 先得到能试用的 Agent | 先把需求/知识/设计做扎实 |
| 价值出现 | 很早（POC 可跑） | 较晚（链路走完再生智能） |
| 改法 | 试用中反向改结构 + **一键同步** | 按步骤推进文档 → 本体 → Agent |
| 本次态度 | **新增，重点验证** | **保留**，同一房间可切换，不废弃 |

- **同一房间、两套用法**，不是两个产品。  
- 用户可从快路径 **代入 / 升格** 到正式四步环境；也可在正式环境里 **降到 / 切到** 快路径继续试。  
- Demo 的第二条主路（UJ-2）就是专门用来验证这套「双模 + 互通」的。

## 2. 三条主路径 = 三大验证点（实际是「大而收束」）

不是七条平行故事。是 **三个大验证**，demo 上收束讲清楚：

| 路径 | 要验证什么 | 里面有没有分支 | 状态 |
|---|---|---|---|
| **UJ-1 半成品续作** | 带着进度进房：资产结构一览 + 对话痕迹 + 下一步；证明「不是文档清单」 | 单线（可在房内切快/正式） | **要验证** |
| **UJ-2 主界面进房** | **先进 Codex 式自由对话**；场景在侧栏承载（可选）。聊着也能长出新场景。**选定场景要打造之后**再选 Fast / 逐步 | **两分支在「进打造」后：2A Fast / 2B Steps** | **要验证（改版主战场）** |
| **UJ-3 Live 迭代** | 已上线后是迭代不是重开；和反改/同步同一套思维 | 单线 | **要验证** |

**收束意思：** 入口只有这三类；快/正式不在工作台再开第三、第四个大门，而在 UJ-2（以及房内）展开。

**不做：** 不为快/正式各做一条独立工作台入口。

```text
工作台
  ├─ Continue crafting ──────────► 主界面（可带场景上下文）→ 选模式 → 打造房
  ├─ Enter Workshop ─────────────► UJ-2 主界面 = Codex 自由对话
  │                                  ├─ 侧栏：已有场景承载（随时可选）
  │                                  ├─ 也可不选：闲聊 / 聊出新场景
  │                                  └─ 选定「要打造」之后才选模式：
  │                                        ├─ 2A Fast（先试跑再改前置）
  │                                        └─ 2B Steps（文档→本体→Agent）
  └─ Iterate（Live）─────────────► UJ-3 迭代（同打造房语境）
```

**归根结底：** 在 Codex 式对话上，增加 AgentOS 的 **交付物 / 资产承载与管理**；不是做成「场景卡大厅首页」。

## 3. UJ-2 细说（先主界面，进打造后才双模）

### 第一部分 · 主界面（进门 = Codex）

1. 工作台 Enter Workshop → **自由对话框**（想聊需求就聊需求，想闲聊就闲聊）。  
2. **已有场景**有一个承载处（侧栏/抽屉均可）：随时可选一个去打造。  
3. **也可以不选场景**：纯聊天；聊着可以 **长出新场景**，再进入打造。  
4. 此时重点是灵活，**不是**一进门就摊开完整资产管理。

### 第二部分 · 选定场景后，再选打造模式

---

### 分支 2A · 快速模式 Fast（新增 · 核心）

1. 先给 **基础文档** + **完整需要哪些东西的框架**。  
2. **尽快试跑**出 Agent。  
3. 试用中发现不足 → **再回头改前置依赖**（文档、本体、Skill…）。  
4. 改任意一点 → **全局联动**；可 Sync。  

**要证明：** 先有可感价值，再深挖依赖；仍是 Codex 对话 + 资产承载。

---

### 分支 2B · 逐步模式 Steps（原四步法保留）

1. 资产承载 **一点点多出来**，并标明 **完整度需要哪些**，照着做。  
2. **重点在文档前置**（需求 / 知识 / 产品设计 / 本体设计 / Agent 设计…）→ **本体图谱** → **再生 Agent**。  
3. 改任意一点 → **全局都会改**（关联交付物联动）。  

**要证明：** 长链路仍在，但不靠死 wizard；有完整度地图可跳可回。

---

### 2A ↔ 2B 互通

| 方向 | 白话 |
|---|---|
| 快 → 逐步 | 试跑后前置缺口清楚，可切 Steps 按完整度补文档/图谱 |
| 逐步 → 快 | 文档做到一半仍可切 Fast 先跑一版 Agent |
| 全局联动 / Sync | 改一个交付物点，关联物更新或标记待同步 |

## 4. UJ-1 / UJ-3（要验证 · 细部待定）

### UJ-1 半成品续作

- **入口：** Crafting 场景 Continue crafting。  
- **进房：** 场景工作区；资产结构 + 对话 + Next。  
- **证明：** 不断档；结构驱动；可点对点补；房内仍可切快/正式。  
- **待定：** 开场是否用它；demo 场景定哪个（例：A1 Supplier）。

### UJ-3 Live 迭代

- **入口：** Live → **Iterate**。  
- **进房：** 已上线基调；可跑可改；可见历史。  
- **证明：** 迭代 ≠ 重开；和 2A「试用→反改→同步」是同一套思维在生命周期后段。  
- **待定：** 和打造中页面差多少信息。
